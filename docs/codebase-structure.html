Querent v2: file structure and software design

Generated from the code at commit 5a60741 (main). Import facts come from parsing every tracked TypeScript file; design claims come from reading the code.

Overview

Querent is one Next.js application (TypeScript, React, Node runtime) with a single SQLite database. A customer chats on the root page; a sales rep works in a portal under /rep. All business logic is under src/server, all SQL is under src/server/repository and src/server/db, and shared types are under src/domain.

How evidence was gathered

Import edges were computed by parsing each tracked .ts/.tsx file with the TypeScript compiler's preProcessFile and resolving @/ (mapped to src/) and relative paths. Type-only imports (import type …) are tracked separately because they disappear at build time.

Top-level shape

Two user interfaces with two architectures. The root page renders one client component, App, that chooses a persona and then shows the customer chat (a single-page app). The rep portal is a set of server-rendered App Router pages under src/app/rep, wrapped by a layout that checks the session.

src/app/page.tsx:1-2, src/components/App.tsx:17
src/app/rep/layout.tsx:21-27

Three API namespaces: /api/query/* (customer and shared), /api/rep/* (rep only), and /api/quotes/[id]/pdf (both, with per-persona rules). Plus /api/session (persona login) and /api/test/* (E2E hooks).

Only one import cycle exists, and it is type-only: server/upsells/rules.ts ↔ server/upsells/wording.ts. There are no value-level cycles.

    Design principles and patterns

    Used by the code

    Layered architecture. One request crosses four layers: route handler → service → repository → database. Example: Approve & send.

    src/app/api/rep/quotes/[id]/send/route.ts:14-22 → src/server/rep/quote-send.ts:68-80 → src/server/quotes/service.ts:133-160 → src/server/repository/quotes.ts:202-210

    Repository pattern, with SQL confined by a test. Every runtime SQL statement is in src/server/repository (seed SQL is in src/server/db). An architecture test scans all files and fails if SQL or a better-sqlite3 import appears elsewhere.

    src/server/repository/boundary.test.ts:4-7
    importers of src/server/db or repository/sql (non-test, computed)

    Facade with a reduced interface (least privilege). repository/customer.ts re-exports only customer-safe functions. Chat tools, customer routes and server/customer/* must import it instead of the full repository (rules 3–6 of the boundary test, checked transitively).

    src/server/repository/customer.ts:7-13

    Functional core, imperative shell. Business rules are pure functions (no I/O, no server-only); a thin service.ts loads facts and calls them. This pairing repeats in pricing, floors, upsells, quotes and analytics.

    src/server/pricing/service.ts:24-39 (shell) → src/server/pricing/engine.ts:118 (core)
    pairs (computed: server-only flag)

    Barrels as client-safe public APIs. Folders expose a pure index.ts for browser and server use, and keep database access in a separately imported service.ts.

    src/server/floors/index.ts:1-5

    Dependency injection by parameter. There is no container. Functions take optional collaborators and the clock (now), with production defaults: the model client, the model name, the date, the distance provider, the wording writer, and env.

    src/server/chat/live.ts:24-35
    src/server/freight/distance.ts:12
    src/server/rep/quote-upsells.ts:80-84

    Strategy. Interchangeable implementations behind one shape: scripted vs live chat engine (same ChatReply), DistanceProvider (haversine today), and ChipWriter (Claude or none).

    src/server/pipeline.ts:47-50

    State machine as a table. Legal quote status moves are data; every service asks assertEvent before writing.

    src/server/quotes/lifecycle.ts:28-33, 58-62

    Optimistic concurrency control. Status writes are compare-and-set (WHERE status=?); send also compares updated_at and the revision and total the rep confirmed.

    src/server/repository/quotes.ts:209, src/server/quotes/service.ts:143

    Idempotency keys. Rep send, duplicate, and customer accept/request-changes accept an Idempotency-Key header and replay the first result. Request quote is idempotent per pop-up message instead.

    src/server/rep/quote-send.ts:59, 72

    Schema validation at boundaries. zod validates untrusted input in 8 server files, using z.strictObject so unknown fields (for example a price sent by a customer) are refused. The model's tool schemas are generated from the same zod schemas that validate the model's input.

    files importing zod (non-test, computed)

    Typed errors mapped to HTTP in one place. QuoteActionError carries a code; a table maps code to status; repError turns it into a response.

    src/server/quotes/errors.ts:6-19, src/server/rep/http.ts:36-39

    Higher-order route wrappers for authorization. repRoute and customerGet resolve the session and pass only the server-derived id to the handler, never an id from the request.

    src/server/rep/http.ts:45-53

    Immutable snapshots and an append-only log. Each send stores a frozen JSON revision that is never updated; quote_activity only receives inserts.

    src/server/repository/quotes.ts:223-231

    Graceful degradation. Model wording is optional: a template is always computed first, and any failure, timeout, or bad output keeps the template.

    src/server/upsells/wording.ts:91-94

    Architecture fitness tests. Rules about who may import what are executable tests, not just conventions (repository/boundary.test.ts, pdf/boundary.test.ts, repository/customer.test.ts).

    Violated or ignored

    Don't Repeat Yourself (DRY). Small helpers are copied rather than shared: firstName in 12 files, a USD Intl.NumberFormat in 15+ files, round2 in 4 files with two formulas, cents in 4 files with two meanings, pricedSubtotal twice with different rounding.

    firstName definitions (computed)
    rounding and money helpers (computed)

    Dependency direction (lower layers should not depend on higher ones). A server service imports from src/components; seed data imports business engines; customer code imports a rep module. See the Dependency Map.

    Names that describe what a module is. src/server holds both server-only code and pure modules the browser imports (server/pricing, server/rep/quote-math.ts, server/quotes/lifecycle.ts). The folder name does not tell you whether a file is safe for the browser; only the import 'server-only' line does.

    Shared contracts in one place. src/domain says it holds the types shared by server and UI, but the UI also imports many response types directly from server-only service files (type-only), for example QuoteDetail from server/rep/quote-detail.ts and RepSettings from server/rep/settings.ts.

    src/domain/index.ts:1-2
    examples (computed, type-only)

    Consistent input validation and error handling. zod is used in 8 files, but the chat route, settings, and query-string parsing validate by hand. Errors use at least five different classes or shapes: QuoteActionError, QuoteRequestError, SettingsError, FloorPermissionError, ConversationNotFoundError, plus {ok:false,status,detail} result objects in the PDF code.

    src/app/api/query/[...path]/customer.ts:23
    src/server/rep/settings.ts:66-70, 141-143

    No hidden global state. Several module-level singletons hold state for the life of the process: the database connection, two idempotency stores, two Anthropic clients, the wording cache, and a heartbeat timer on globalThis.

    singletons (computed from code)

    One routing convention per API. Customer endpoints are split between a catch-all handler (/api/query/[...path]: chat, history, notices, me, erp/status) and file-based routes (/api/query/customer/quotes, quote-requests, and others). The catch-all exports PUT, but no branch handles it.

    src/app/api/query/[...path]/route.ts:14-22

    Consistent formatting. There is no linter or formatter config. Most files use a dense one-line style with single quotes; pipeline.ts and Chat.tsx use Prettier-style double quotes. 56 production lines exceed 250 characters (the longest is 1,157, in schema.ts).

    Code health

    Ranked by risk to a future integration (connecting Querent to an ERP, real authentication, or other services). HIGH: likely to break or mislead an integration. MEDIUM: will slow it down or cause subtle defects. LOW: cleanup.

    Checked and found clean

    No unused runtime dependencies: every entry in dependencies is imported by production code. Dev dependencies without imports (@types/*, jsdom, tsx, typescript) are used by tooling (the Vitest environment, the db:reset script, the compiler).

    No orphan production files: every non-entry source file is imported by at least one production file, except test fixtures and test helpers.

    No unused local variables or parameters in production code (tsc --noUnusedLocals --noUnusedParameters).

    Questions for you

    1. What is the integration: an ERP sync writing into the ERP_SOURCED_TABLES, another service reading quotes, or both? That decides whether the repository or the API is the integration surface.
    2. Will integration code run inside the Next.js process, or as a separate worker? A separate process cannot import most of src/server as-is (server-only, singletons).
    3. Should auto-seeding on an empty database be turned off outside demo environments?
    4. Do you want the browser-safe modules moved out of src/server (for example to src/core) before more code depends on the current paths?
    5. Should shared formatting and rounding helpers be consolidated now, given money rounding differs between modules?
    6. Is a database migration tool in scope? Today a schema change requires deleting the database.
    7. Should the ERP status indicator be removed or wired to a real signal until an ERP exists?
