Querent v2: request path from chat message to quote

An evidence-based reading of the code at commit 5a60741 (main). The code is the only source of truth used here.

Overview

This page traces one request through the backend: a customer types a message, the model answers with the help of tools, the customer confirms a list of items, the server drafts and prices a quote, a rep reviews and sends it, and the customer sees it. Every claim has a label and a file citation you can expand.

The most important finding

The model never creates a quote and never sets a price. In live mode, the model (Claude) can only read data through 7 tools and propose an item list (propose_cart). That proposal is stored as an item pop-up message. A quote is created only when the customer presses Request quote, which calls a separate HTTP endpoint with no model involved. That endpoint validates the input against the stored pop-up, prices every line with a deterministic pricing engine, and writes the quote in one SQLite transaction.

System at a glance

One Next.js app (Node runtime) serves both the customer chat and the rep portal. All data is in one SQLite file opened with better-sqlite3 (synchronous), WAL mode, foreign keys on. There are no migrations: a database with another schema version refuses to open.

Problems found while reading

GAPpropose_cart accepts any SKU that exists in the catalog. It does not check that the SKU came from search_items or from the clarify state. The "use only matched SKUs" rule is in the prompt and tool description only. The checks that follow are the customer reviewing the pop-up and the rep reviewing the draft.

src/server/chat/tools.ts:229-236

GAPIn live mode, a successful propose_cart wins over an open clarify state: finish() checks the pop-up before the request state. So the model can open the pop-up while lines are still open, and the open lines are dropped.

src/server/chat/live.ts:150-154

DIVERGENCELive and scripted engines differ when the last open line gets matched. Scripted mode calls requestReply, which opens the pop-up automatically once nothing is open. Live mode calls requestReply only when request.open.length is non-zero; if every line is now matched but the model did not call propose_cart, the reply is plain text and the matched cart is not stored anywhere. How the model learns tools exist, and how results return

The model learns about tools only from the tools parameter (name, description, JSON schema) and from the system prompt, which names search_items, get_stock, get_price, get_order_history and propose_cart. Results return as tool_result blocks in a user message whose tool_use_id matches the request. Successful data is JSON.stringify(result.data), unformatted.

Growth, trimming, summarization, limits

Across turns: trimmed by message count only (last 20 text messages). No token counting, no summarization. Tool data from earlier turns is never re-sent, so the model sees earlier facts only through its own earlier text. system-role messages (the "quote is ready" notices) are excluded from history.

Within a turn: the message list grows by two messages per tool round, up to 6 rounds. Tool result size is bounded only by tool limits (e.g. search_items: up to 20 lines × up to 20 candidates; get_order_history: up to 50 lines). Output is bounded by max_tokens: 16000 per call.

The clarify state is the one piece of structured memory carried across turns, and it lives only in the payload of the last assistant message. Any reply that is not a clarify reply (for example an off-topic answer, or the error reply) ends the pending request.

Prompt caching: the cache marker is on the system block, so the cached prefix is tools + system. Because the system prompt contains today's date and per-customer data, the cache is per customer per day. The cache benefit within a turn's tool rounds is real; across customers it is none.

If a stored turn has a customer message but no assistant message (crash during a model call), history will contain two consecutive user messages. Whether the API accepts or merges them is not shown in this code.

Quote and database

How a quote is created, validated, calculated and stored

  1. Created only by requestQuote() (customer click), duplicateQuote() (rep menu) or the seed. Not by the model.
  2. Validated against the strict body schema and the last stored item_popup payload (step 13).
  3. Calculated by the pricing engine (step 14). Totals are not stored on the quote; list views compute sum(qty*unit_price) in SQL, and the send computes the snapshot total. Freight is computed on read; only a rep override is stored.
  4. Stored in one transaction (step 15). Each send stores an immutable revision snapshot (step 19).
